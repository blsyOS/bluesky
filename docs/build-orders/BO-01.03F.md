# BO-01.03F — BlueSky Locate Foundation & Product Navigation

**Status:** Complete
**Phase:** 01 – Platform Foundation
**Depends on:** BO-01.01 → BO-01.03E

## Purpose

Introduce product-specific navigation across BlueSky OS and stand up the
first production product, **BlueSky Locate**, as a complete-feeling
application (own sidebar, dashboard, Contacts module, module shell) that
still shares the platform architecture. This is the blueprint every future
product (Storm, Leak, Dispatch, Fleet) follows. **The dashboard engine and
all registries from prior build orders are unchanged.**

## Product context system

Products are independent applications within BlueSky OS. A product declares
its own navigation; the shell renders whatever the active product's config
specifies.

```
src/lib/products/
  types.ts        ProductNavConfig, NavSection, NavEntry (icon, featureFlag)
  registry.ts     ProductRegistry + resolveSidebar() (feature-flag gating,
                  global Administration appended)
  admin-nav.ts    ADMIN_SECTION (Products, Users, Roles, Audit Logs, Settings)
  configs/        platform | locate | storm | leak product configs
  index.ts        registers all configs; exports PRODUCT_COOKIE, defaults
```

- **The sidebar is generated entirely from product configuration** — no
  hardcoded module nav. `resolveSidebar(config, ADMIN_SECTION)` returns the
  product's sections (feature-flag-gated) plus the global Administration
  section. New products register a config; shared sidebar code is untouched.
- **ProductContextSelector** (topbar, replaces the old ProductSwitcher):
  switching a product persists the choice (`bsky_product` cookie, read
  server-side in the layout so SSR renders the right sidebar with no flash),
  tells the shell to rebuild its sidebar, and navigates to the product's
  `defaultLanding`. Breadcrumbs and page titles update from the routes the
  product exposes.
- Icons are React components, so configs are a **client registry**; the
  server layout only passes the active product id (a string) across the RSC
  boundary — no function serialization.

Each product config declares: name, icon, accent, default landing, sidebar
sections, and feature flags.

## Product sidebars

- **Platform** — Workspace (Dashboard) + Administration.
- **BlueSky Locate** — Workspace (Dashboard) + Modules (Locate, Storm, Leak,
  Dispatch, Fleet, **Contacts**, Reports) + Administration.
- **BlueSky Storm** — Workspace (Dashboard) + Modules (Storm, Fleet, Reports)

## Contacts (BlueSky Locate only)

Renamed from "Customers". Contacts is the operational contact directory used
by locating companies — not a general CRM. It is **exclusive to BlueSky
Locate** via the `contacts` feature flag (enabled only in the Locate config),
so it never appears in Storm/Leak/other products' sidebars.

- **Data model** (`prisma`, `Contact`): general info (organization, contact
  name, title, department, type/subtype, status), communication (office/
  mobile/email/fax), addresses (billing/mailing/physical), operational
  (utility served, service area, counties/states, notes). Attachments,
  agreements, insurance, and certificates are noted as future-ready and not
  modeled yet.
- **Contact taxonomy** (`src/lib/contacts.ts`): seven groups — Utility
  Owners, Municipalities, Contractors, Engineering Firms, Property Owners,
  Emergency Contacts, Internal Contacts — each with subtypes. Adding a group
  never touches other code.
- **UI** (`/contacts`): type-filter chips with counts, a create form
  covering the full record, a grouped directory table, and a professional
  empty state. Contact data is user-entered; **no records are seeded**.
  Creating a contact writes an audit-log entry.

## Locate product

- **Operational dashboard** (`/dashboard/locate`): Today's Tickets, Ticket
  Status, Active Locators, Upcoming Due, Damage Investigations, and a Recent
  Activity widget (reuses the ActivityCenter). Every operational widget is an
  honest empty state naming the future module that supplies it — **no
  fabricated numbers**.
- **Locate module shell** (`/locate/*`): a secondary nav (Dashboard,
  Tickets, Assignments, Maps, Damage Investigations, Reports) over
  professional empty-state pages (`ModulePlaceholder`), each explaining what
  will appear and which module delivers it.
- **Reports landing** (`/reports`): names the future report categories
  (Ticket Production, Damage Reports, SLA Compliance, Locator/Utility/
  Dispatch Performance, Fleet) as coming-soon cards. No reporting engine yet.

## Preserved architecture (unchanged)

Dashboard Registry, Dashboard/Widget Providers, Dashboard routing, role
routing, the search/notification registries, and the responsive sidebar
shell mechanics are all reused as-is. No dashboard logic was duplicated —
Locate widgets and the Locate dashboard render through the existing engine;
the Contacts directory reuses the shared table/card/form components.

## Extension points

A new product = a new `ProductNavConfig` (register in `products/index.ts`)
plus, optionally, dashboard/widget providers. No shared sidebar, shell, or
engine code changes. Feature flags gate optional modules per product.

## BO-01.03F.1 — Product Context Selector Cleanup

Correction applied after approval: **product switching is administrative
context, not navigation.** The topbar product selector was removed; the
active product is now switched only under **Administration → Settings →
Product Context** (an Active Product dropdown). The sidebar shows the
active product name + icon as a read-only context row beneath the company
card. Switching still updates the context, rebuilds the sidebar from the
product's configuration, opens the product's default dashboard, updates
breadcrumbs/titles, and persists via the `bsky_product` cookie — the
mechanics moved into a shared `ProductContextProvider`
(`src/components/shell/product-context.tsx`) consumed by both the shell
and the Settings panel. No registry, engine, or config changes.

## Known limitations

- The product-context selector lists all configured products; it is not yet
  gated by company license (deferred; the licensing data already exists).
- Contacts route is reachable by deep link regardless of active product;
  exclusivity is enforced in navigation (per the build order).
- Locate operational widgets and module pages are empty-state shells until
  the Locate ticketing/dispatch build orders land.
- Contact edit/delete and attachments are future work (create + list only).
