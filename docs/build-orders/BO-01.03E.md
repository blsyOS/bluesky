# BO-01.03E — Operational Dashboard Migration

**Status:** Complete
**Phase:** 01 – Platform Foundation
**Depends on:** BO-01.01 → BO-01.03D

## Purpose

Turn the dashboard *framework* from BO-01.03D into a production-shaped
operational command center. The Platform dashboard now answers "what
requires attention right now?" instead of showing a product catalog, and
dashboards are chosen by the authenticated user's role. Module dashboards
(Locate, Storm, Leak, Dispatch) are scaffolded with honest empty-state
widgets; Fleet, Customers, Reports, and the role dashboards register as
empty surfaces. **The dashboard engine from BO-01.03D is unchanged** —
this build order only adds catalog/routing data, providers, and cleanup.

## What changed (and why)

- **Products removed from the Platform dashboard.** Products live in the
  sidebar; the dashboard is the command center. The generic-SaaS metric
  cards (Products/Users/Roles/Audit counts) were removed.
- **Operational sections added**: Operations (Active jobs, Active users,
  Today's work, Open alerts), System (API health, Queue status,
  Notification services, Background jobs), Quality (Failed jobs,
  Validation errors, Sync issues, Processing errors). None of these have
  a backend yet, so **every one renders an empty state that explains when
  the data will connect** — no invented numbers.
- **Activity** reuses the BO-01.03C `ActivityCenter` with real audit-log
  entries loaded server-side (`loadPlatformStats`). No duplicate feed.
- **Role-based routing**: `/dashboard` resolves the landing dashboard from
  the user's roles (`resolveDefaultDashboard`). Seeded roles → Platform;
  future roles map (dispatcher → Dispatch, locator → Locate, storm_manager
  → Storm, …). Falls back to Platform.
- **Module/role dashboards** are reachable at `/dashboard/<id>` and shown
  in the sidebar (Modules section). Scaffolded dashboards render
  empty-state widgets (Locate/Storm/Leak/Dispatch) or the engine's
  "coming online" empty state (Fleet/Customers/Reports/role dashboards).
- **Widget cleanup**: removed the framework-testing **Configure**
  placeholder screen and session-only **Hide Widget** action (and their
  `WidgetActionContext` methods). Retained **View Details**, **Refresh**,
  and **Retry** (widget-defined). Empty widgets now render a compact
  "awaiting data" form (a muted em-dash + explanation) instead of the
  large icon empty state.

## Architecture (unchanged engine, new data/providers)

```
src/lib/dashboards/
  catalog.ts        Server-safe DASHBOARDS map (13 ids), kinds, MODULE_NAV_IDS,
                    isDashboardId — used by routing, breadcrumbs, tests
  roles.ts          resolveDefaultDashboard / defaultDashboardForRole (pure)
  platform-stats.ts Server loader (audit activity only; no fabricated data)
  providers/
    platform.tsx    Operational Operations/System/Quality (empty) + Activity
    module.ts       registerModuleDashboard() scaffolding factory
    locate|storm|leak|dispatch.ts   empty-state module dashboards
    index.ts        registers all providers + scaffold-only layouts
src/components/dashboards/
  dashboard.tsx     (engine — hide logic removed, otherwise intact)
  widget-card.tsx   (Configure/Hide removed; compact empty state)
  dashboard-view.tsx  client host; imports the providers index
src/app/(app)/dashboard/
  page.tsx              role-resolved landing (platform by default)
  [dashboardId]/page.tsx specific dashboard by id (scaffolded empties)
```

Data reaches the engine the same way as BO-01.03D — through the open
`DashboardContext.data` bag. Only the Platform dashboard needs data
(audit activity); scaffolded dashboards render with none.

## Widget standards

Every widget supports Loading, Empty, Success, and Error states
(`WidgetCard`/`WidgetBody`). Operational widgets without a backend use the
Empty state with an explanatory message; the Error state stays available
for genuine failures (with an optional Retry action). Rendering never
fails because a provider returns nothing — the dashboard falls through to
its empty state.

## Extension points (unchanged)

`registerDashboardProvider`, `registerWidgetProvider`,
`registerCategory` / `provider.categories`, `widget.actions`,
`DashboardContext.data`, and `<Dashboard context={{dashboardId}}/>`.
A module build order replaces its `registerModuleDashboard(...)` empties
with a real widget provider — no engine or routing changes required.

## Known limitations

- Operational widgets are intentionally empty until their modules ship;
  they explain the data source rather than showing values.
- Role routing has no persistence/override yet (user preferences are a
  later build order); the mapping is role → dashboard only.
- Scaffold-only dashboards (Fleet, Customers, Reports, role dashboards)
  show the engine empty state until their build orders add widgets.
- Per-provider failures remain silently isolated (by design); no
  partial-failure banner yet.
