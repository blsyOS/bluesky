# BO-01.03D — Dashboard Framework

**Status:** Complete
**Phase:** 01 – Platform Foundation
**Depends on:** BO-01.01 → BO-01.03C

## Purpose

The universal dashboard engine for BlueSky OS. Every future surface —
LocateOS, LeakOS, FiberOS, SiteView, Command Center, Administration,
People Development, Reports — registers dashboards and widgets into this
framework instead of building its own. This build order ships the engine,
widget system, and a placeholder platform dashboard only: no real KPIs,
no charts, no drag-and-drop, no persistence.

## Architecture

Same extension philosophy as Search (BO-01.03B) and Notifications
(BO-01.03C): registry → provider → common interface → failure isolation →
lazy registration.

```
src/lib/dashboards/
  types.ts        DashboardProvider, WidgetProvider, DashboardWidget,
                  DashboardWidgetCategory, DashboardContext,
                  DashboardLayout, WidgetAction(+Context), WidgetStatus,
                  WidgetSize, WidgetState, WidgetMetric/Trend
  registry.ts     DashboardRegistry + app-wide singleton;
                  loadSections() fans out with Promise.allSettled,
                  drops disabled widgets, orders categories then widgets
  categories.ts   CORE_WIDGET_CATEGORIES (overview, operations, quality,
                  safety, people, training, financial, products, system,
                  activity)
  providers/
    platform.tsx  Platform dashboard + widget provider (placeholder
                  widgets over existing seeded data)
src/components/dashboards/
  dashboard.tsx           The engine surface: loads sections, responsive
                          grid, loading/empty/error states, session-only
                          widget hiding, refresh
  widget-card.tsx         WidgetCard + action menu + config placeholder
  platform-dashboard.tsx  Client host wiring server-fetched stats into
                          DashboardContext.data
```

**Data flow:** the host page (a server component) fetches whatever data
its widgets need and passes it through the open `DashboardContext.data`
bag. Each provider owns the shape of the keys it reads (the platform
provider exports `PlatformDashboardData`); the engine stays generic and
never learns module data shapes.

## Widget system

`WidgetCard` supports: title, subtitle, description, icon (accent-aware
tile), category (drives the section), product accent via `accentKey` →
`accentStyle()`, status badge (coming-soon renders dimmed with an inline
empty state), body states (`ready` / `loading` skeleton / `empty` /
`error` with `role="alert"`), optional metric value with trend indicator
(reuses the KpiCard `TrendIndicator`), custom `render()` body, footer,
"updated … ago" timestamp, an Open link, and the action menu.

**Sizes → grid footprint** (grid: 1 col mobile, 2 cols ≥sm, 4 cols ≥xl):
small = 1 col, medium = 2 cols on desktop, large = 2 cols from tablet,
wide = full row.

**Action menu** (keyboard accessible, `usePopover`): View Details
(placeholder toast), Refresh (re-runs provider loading), Configure (flips
the card to the configuration placeholder, which states that sizing/
thresholds/data options arrive with user dashboard preferences), Hide
Widget (session-only, toast explains it returns on reload). Widgets can
prepend their own `WidgetAction`s — e.g. the error-state demo widget adds
Retry.

## Placeholder platform dashboard

`/dashboard` now renders through the framework. Widgets over existing
seeded data: Products enabled, Users, Roles, Audit activity (Overview
metrics), Your products (large, custom render with product glyphs +
status badges), Performance trends (coming-soon demo, Command Center
accent), System status (empty-state demo: "No incidents reported"),
Connected services (error-state demo with Retry), Recent activity (wide,
**reuses `ActivityCenter`** from BO-01.03C with real audit-log entries —
no duplicated feed component).

## Extension Points

| Seam | How future modules plug in |
| --- | --- |
| Dashboards | `dashboardRegistry.registerDashboardProvider()` |
| Widgets | `registerWidgetProvider()` (side-effect import) |
| Categories | `registerCategory()` or `provider.categories` |
| Widget actions | `widget.actions` prepend to the standard menu |
| Data | `DashboardContext.data` bag, provider-owned shapes |
| Surfaces | `<Dashboard context={{dashboardId}}/>` hosts product/company/user/manager/executive dashboards by id |

## Known Limitations

- Widget hiding and refresh are session-only; layout/preferences
  persistence is a later build order (drag-and-drop explicitly deferred).
- The configuration surface is a placeholder panel.
- The dashboard-level error state guards engine faults; per-provider
  failures are silently isolated (by design) with no partial-failure
  indicator yet.
- Widget `render()` bodies execute client-side; server-only data must be
  serialized through `DashboardContext.data`.
- No virtualization; fine at placeholder volumes.
